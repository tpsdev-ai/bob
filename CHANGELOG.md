# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Fixed

- **`bob install-service` writes a stable Node path, not a versioned Homebrew Cellar target (bob#228).** When the installer IS Node, the unit's interpreter is resolved to the STABLE PATH entry that resolves to the same binary — for example `/opt/homebrew/bin/node`, not `…/Cellar/node/<version>/bin/node` — compared by realpath so a PATH `node` symlinked to a DIFFERENT binary is not chosen. With no PATH entry resolving to the running interpreter, the resolution falls back to the installer's own `execPath`; when the installer is not Node (e.g. bun), the first `node` on PATH is used as before. A `brew upgrade node` no longer strands the unit. Both renderers (launchd and the systemd user unit) use the one resolution. (`test/shell/service.test.ts`)

- **The discord capability can make REST calls again under the global undici 8 override (bob#217).** The capability's Discord client now hands discord.js's REST manager its own request function, which performs the call with the runtime's global `fetch`. @discordjs/rest's own request strategy builds the response with `new Headers(res.headers)`; under Node the pinned `undici` negotiates HTTP/2, Node's HTTP/2 client marks that headers object with a `Symbol(sensitiveHeaders)` key, and undici's `Headers` constructor rejects a symbol key — so on the override as it stands no REST call can complete, and that REST failure blocks the agent's gateway from being set up (opening the gateway is a later, separate stage). The global `fetch` does not go through the pinned `undici` package, so the request completes. The request function forwards only the method, the body, the string-keyed headers and the abort signal: it drops any dispatcher the manager supplies (this binding never sets an agent, and a dispatcher from the pinned `undici` is incompatible with the runtime's `fetch`), and it refuses to follow redirects, so a cross-origin 3xx fails with the status and the target host instead of letting the request leave unauthenticated. `bun audit` stays clean. (`test/capabilities/discord/rest-connection.test.ts`, `test/capabilities/discord/rest-request.test.ts`)
- **The installed service unit runs bob under Node, with an absolute interpreter path resolved at install time (bob#218).** `bob install-service` writes `<node> <bob> run <name>` into both the launchd `ProgramArguments` and the systemd `ExecStart`, where `<node>` is an absolute Node executable — the installer's own interpreter when it is Node, otherwise the `node` found on the installer's PATH. launchd and systemd both launch a unit with a minimal PATH, and bin/bob's `#!/usr/bin/env node` shebang resolved the interpreter through that PATH — so a node installed outside `/usr/bin` (Homebrew, nvm) was not found and the job exited 127, restarting every throttle interval without ever starting the agent. A bun-launched install no longer writes a unit that runs bob under bun (bin/bob's shebang and the package's `engines` require Node): installation REFUSES, naming the remedy, when no Node is found, and writes nothing. An already-installed unit keeps its old command until it is rewritten, so reinstall it after an upgrade (`bob down <name>`, `bob install-service <name>`, `bob up <name>`). The unit still embeds no secret. (`test/shell/service.test.ts`)
- **A resident agent keeps a tool only when a reviewed classification says it writes no file and runs no command (bob#213).** Every tool an agent's allowlist can name (pi's built-ins and every tool a blessed capability's manifest declares) has a reviewed row in `TOOL_EFFECTS` (`src/shell/tool-allowlist.ts`): `read-only`, `writer` (writes a file the model names, or runs a command) or `effect` (a memory write, a Discord post or reaction, a status report, a robot action, cancelling a job this run started). `RESIDENT_EXCLUDED_TOOLS` is derived from it: every `writer`, plus any declared name without a row. It now includes anchored-edit's `write_file`, `edit_lines` and `insert_after` beside `bash`, `write`, `edit`, `powershell` and `run`, so a resident agent without its role's `allowResidentShell` opt-in no longer keeps them; builder-local, the one shipped role that lists them, opts in. A test enumerates the manifests' tools and fails on a name without a row, and on a row no manifest or pi built-in provides. (`test/shell/tool-allowlist.test.ts`)
- **`run` refuses a `cwd` outside the workspace (bob#213).** The `cwd` is resolved through symlinks, and a directory outside the workspace is refused, naming the workspace and the resolved path; nothing starts. A directory inside the workspace whose name starts with two dots (`..cache`) is accepted. Tests cover a relative path inside, a `..` escape, a `..cache` directory, and a symlink inside the workspace to an existing directory outside it. The `cwd` parameter description and the capability README name both accepted forms: relative to the workspace, or an absolute path inside it. (`test/capabilities/work/boot-sweep.test.ts`)
- **`bob init --role builder-local` stamps neither `bash` nor `run` (bob#213).** A test pins the stamped list (`grep`, `find`, `ls` and the three Flair tools) and shows the run tools are stamped only when `work` is among the capabilities; the `work` capability's README says it is what enables `run`. (`test/shell/init.test.ts`)
- **README: where a restarted agent reports what a crashed run left (bob#213).** The boot sweep logs each job a crashed run left that it can inspect to the runtime log and attempts to record it in the job's registry record (`reaped_by`, a write that can fail); none of it enters the restarted session's model context. The README now says so.
- **Flair Soul provisioning now uses operator Basic auth.** `bob onboard` and `bob align` read the operator password from `~/.flair/admin-pass` at each Soul push (`--admin-pass-file` overrides the path; `--admin-user` overrides `admin`). `bob align` requires an operator-supplied `--flair-url` matching the agent's configured URL. Basic auth is sent only to HTTPS or numeric loopback HTTP targets, and Soul writes refuse redirects. The divergence read stays agent signed and still saves the previous persona byte for byte on conflict. A missing password file fails with an actionable path and remedy. The operator password is read at call time, removed from the process environment and never passed to an agent session: bob takes `FLAIR_ADMIN_PASS` out of its environment at startup and hands the value only to Agent registration, and bob's session factory removes the variable again before any session (the hiring and onboarding interviews, align, run, launch) is built. It is not isolated from same-user file access, which is tracked separately, nor from a same-user process that reads bob's initial environment. This fixes `403 soul_write_requires_operator` on current Flair. (`test/shell/flair-soul.test.ts`, `flair-provision.test.ts`, `operator-credential-env.test.ts`, `test/cli.test.ts`)
- **Operator-authorized Flair requests never print the server's response or a transport error.** A failed ops-API registration request now reports its status, operation, table and where the operator credential came from (`FLAIR_ADMIN_PASS` or the admin-pass file), never the response body, which is not read; the Soul writer follows the same rule. An exception from sending a registration or Soul request, or from reading its response, is replaced by an error naming only the operation, the target origin and the remedy, with no cause attached. Tests cover registration and Soul writes, directly, through `onboard` and `align`, and through the built CLI, and assert that no form of the credential reaches the error, stdout or stderr. (`test/shell/flair-pair.test.ts`, `flair-soul.test.ts`, `flair-provision.test.ts`, `test/cli.test.ts`)
- **Agent registration no longer reports a repair it did not make.** A refused Agent insert is treated as a concurrent registration only when a fresh read finds the Agent record; otherwise the insert's own error is reported. After updating a record's public key, registration reads the record back and reports `repaired` only when it carries the requested key. If the update request fails or the update did not take effect, registration fails and reports the insert error when an insert was refused. (`test/shell/flair-pair.test.ts`)
- **The setup sessions replace pi's unrestricted `write` with a bob-owned, soul-only `write_soul` (bob#204).** `bob onboard`'s hiring interview and `bob align` added pi's generic `write` so the interview could write the agent's refined `soul.md` — but pi's `write` accepts ANY absolute path the OS user can write, so a setup session could rewrite `bob.yaml`, capability overrides, grants, launcher scripts, or files outside the agent directory. Every setup session — an ordinary agent's and an ADOPTED agent's alike (not the grant's tools plus `write`) — now runs exactly `read` + `write_soul`: a bob-owned tool (`src/shell/write-soul.ts`) that takes `content` and nothing else (every other argument key is refused, and its schema allows no other property). Its one target is `soul.md` in the directory the session runs as. Before the session starts, bob canonicalizes the agents root once and uses that one tree for the session's config, its paths and the binding, and it refuses an `--agent-dir` that names a different agent's directory. On every call the tool refuses a symlink in ANY component of that path, caps the content at 64 KiB, writes every byte (honoring partial writes, refusing zero progress), fsyncs, and only then renames over `soul.md`. An existing `soul.md` keeps its permission bits; a new one is `0600`. Threat model, stated: this defends against the setup session's OWN tool calls. The model holds only `read` and `write_soul`, with no shell, and whatever arguments it sends, the one file it can write is the bound `soul.md`. A concurrent local process that renames directories inside the agents tree already has the user's write access and is out of scope. On Linux the temp creation, rename and cleanup go through the open directory handle (`/proc/self/fd`). On macOS, where Node offers no directory-relative calls, they use the path, re-checked immediately before each step; those checks are best effort against such a process, not a guarantee. The temp (`.soul.md.write_soul-<pid>-<24 hex>.tmp`) is created exclusively and held open until the rename is confirmed. On a failure, a call removes only the temp it created (name and inode). Nothing is deleted on name-and-age evidence, so a crash can leave a temp in the agent directory; bob never reads it, and it is safe to delete by hand. Limit, stated: an agent running as the operator's OS user with a shell or unrestricted read can still reach operator files directly — that needs the OS boundary (bob#189), which this does not replace. (`test/shell/write-soul.test.ts`, `onboard.test.ts`, `align.test.ts`, `positions-195.test.ts`)
- **Position hire and grant handling (bob#195 slice 1).** `hire` refuses the unsupported `--flair` flag before scaffolding, including when the flag precedes the agent name; direct hire calls also refuse Flair opt-in. Every grant reader now rejects malformed grant JSON with a named refusal and recovery instruction. Override repository setup ignores operator Git signing, hook and template settings. The hiring interview uses the same host and positions roots as hire validation and binding.

- **Hire and adoption refuse occupied ratification state, and a failed interview fails the hire (bob#195 slice 1).** Ordinary `hire` and `position adopt` refuse an existing grant, binding marker or baseline, naming the occupied paths and the current position when readable. Re-binding is not supported in this slice. Occupancy includes directory entries whose targets cannot be read. Provider/runtime-key, position, role/secret and ratification-occupancy checks run before scaffolding. Rollback removes the new scaffold and recorded binding files after an error, preserving pre-existing agent and override directory entries. Complete transactional cleanup is still needed for writes that fail before returning and additions to existing override directories. (`test/shell/positions-195.test.ts`)
- **Presence stops its beacon on session shutdown.** Repeated shutdown and an already queued beacon callback emit nothing further.
- **Over-limit turn origins fail explicitly.** Mail agent names, cron job names and Discord channel IDs share producer and admission limits; cron names with underscores retain cron attribution.

- **flair-pair derives the registered public key from the private key and refuses a .pub that disagrees.** A Flair-minted `.pub` is RAW 32 bytes (`writeFileSync(pubPath, Buffer.from(kp.publicKey))`), but the reuse path read it as base64 TEXT, so a key directory minted by `flair agent add`/`rotate-key` registered a WRONG public key that could never verify the private key's signatures. `flairPair()` now loads the private key through the normalizer and DERIVES the public key (`createPublicKey`), reads a present `.pub` as BYTES — exactly 32 raw bytes, or strict base64 text decoding to 32 bytes, the same rule as the private key — and REFUSES a `.pub` that does not match the derived key, naming both files and never any key material. With no `.pub`, it creates one holding the derived key (published complete, never replacing an existing file), so deleting a mismatched `.pub` and re-running repairs the pair. (`test/shell/flair-pair-pub-191.test.ts` (p1)-(p8))

- **bob loads the raw 32-byte seed key Flair writes (and base64 of it), as well as base64 PKCS8 and PEM, and a malformed key fails with the file, its size and the accepted formats.** Flair's own tooling (`flair agent add`, `flair agent rotate-key`) writes a bare 32-byte binary seed, but every key reader only accepted PEM PKCS8 or base64 PKCS8 DER, so a Flair-made key failed at signing time with `error:0680008E:asn1 encoding routines::not enough data`. One normalizer (`src/lib/ed25519-key.ts`) now turns all four shapes into PKCS8 DER, and every reader takes the file's BYTES through it; anything unparsable or not Ed25519 is refused naming the path and the byte count, never the key. (`test/lib/ed25519-key.test.ts`)

### Changed

- **`bob onboard` no longer scaffolds `channels.tps_mail`, and `MailConsumer` is the verified tps-mail consumer (#200).** Nothing ever read the `channels: tps_mail:` block, so an onboarded agent looked mail-capable and was not; onboard now writes the `tps-mail:` block only as a commented template (it needs a `senders:` allow-list onboard cannot know), and `bob doctor` FAILS an existing `bob.yaml` that still carries `channels.tps_mail` without the capability. `MailConsumer` now requires the agent's identity, a non-empty `senders` list and a key resolver, runs each turn through `bob launch` in mail-turn mode (stdin, not argv), and replaces `stats.failed` with per-reason counters.

- **Dependency updates are configured through Renovate on the shared tpsdev-ai preset; Dependabot is retired.** bob keeps its stricter install gate: advisory fixes wait the same 7 days as every update (bunfig refuses versions younger than 7 days, except @types/node and typescript), the whole pi runtime family is excluded, lockfile maintenance is off, and CodeQL's sub-actions update as one PR for every update type.

- **The builder-local role's seed soul gains an Operating rules section** (start from the given head, never kill by pattern, report instead of investigating past the brief, never rewrite pushed history, use your own identity, apply-only means apply-only, finish with evidence).

### Added

- **An explicit model budget: context window, compaction between model calls, thinking level, an output-cap backstop, per-request usage (#214).** Measured on a local builder, decode ran about 99 tok/s at 16k context or less and about 44 tok/s above 192k. Contexts ran to the server's limit because the runtime's window (131k) was not the server's (262k) and compaction was only checked when a run ended. bob.yaml's `provider:` block now takes `context_window` (required: every session refuses to start without a window for the provider/model it runs, naming bob.yaml and the key that would declare it), `max_output_tokens`, and `models:` entries for `--model` overrides (`bob run --model` and `bob align --model` both resolve them; `bob align --provider` naming a provider other than bob.yaml's is refused, since bob.yaml declares windows for its own provider only). The declared numbers are what pi's runtime uses for that model. A new `session:` block (`compaction_threshold`, `thinking: off | low | high`) overrides the role's `session` defaults in role.json; `builder-local` ships `0.5` and `low`. The threshold sets pi's own compaction reserve. bob also checks it after every model call that ended in tool calls; over it, bob queues a checkpoint message and ends pi's low-level loop at that turn boundary, so pi's own compaction runs mid-run and the run continues. The thinking level is handed to pi, which sends it to the provider only when pi's model config marks the model as reasoning and the provider's request shape accepts the parameter (for example `reasoning_effort` on the OpenAI-compatible path); whether a server acts on it is the server's behaviour. `max_output_tokens` sets the output cap pi requests, in whichever output-limit field the provider's API uses (for example `max_completion_tokens`, `max_tokens` or, on OpenAI's Responses API, `max_output_tokens`; that API's client raises a cap below 16 to 16); for a server that ignores it, bob adds a backstop that ends the stream as a `length` stop after more streamed pieces than the cap. It counts pieces, not tokens: never early (a server sends a piece only after generating at least one token), possibly late (a piece can carry many tokens). The ended message holds only the pieces bob accepted, and its usage is assigned (`output` = the cap, a lower bound; prompt counts 0), not measured. Every run log carries a `requestUsage` record per request (prompt, cached-prompt, completion and thinking tokens, time to first streamed piece, duration, stop reason, provider and model); the record holds counts and timings, no prompt or response text. `bob onboard` and `bob hire` require `--context-window <tokens>` and refuse without it before writing anything. **Upgrade note:** an existing agent's bob.yaml needs `provider.context_window` (and a `provider.models:` entry for each `--model` it runs) before its next session. Unknown keys in `provider:` are now refused. (`test/shell/model-budget-214.test.ts`, `init.test.ts`, `cli.test.ts`)

- **The `work` capability: builder-local runs commands through a managed `run` tool instead of `bash` (#211, slice 1 of #210).** `run(command, cwd?, timeout_s?, background?)`, `run_status(run_id?)` and `run_cancel(run_id)` (`src/capabilities/work/`, a blessed catalog entry) replace pi's `bash` in `roles/builder-local/role.json`, which now allows `run`, `run_status` and `run_cancel` and not `bash`. Every command has a deadline: an omitted `timeout_s` gets the 600 s default, a larger request is capped at the 3600 s hard maximum (slice 1 has no clamp to a run budget yet; that is #210 slice 4), and a non-positive value is refused by name. The deadline is the tool's own timer: SIGTERM to the job's process group, SIGKILL after a grace, then a check that the group is empty. The command's `outcome` (`exited`, `timed_out` with an `escalated` flag, `signalled`, `cancelled`, `no_exit_status`) and the verified `cleanup_state` (`group_empty`, `group_killed`, `escaped_or_unverified`, `verify_unavailable`) are separate fields, and only `exited` with exit 0 and a clean `cleanup_state` is success. Output is captured, up to a 64 MiB cap, to an owner-only file outside the workspace (same-user readable; deleted at run end), created exclusively (never through an existing file or symlink) in a per-run directory that `mkdtemp` creates 0700 with an unpredictable name; the model sees a bounded tail excerpt passed through bob's existing secret redaction before it is cut, an unterminated final line is withheld until the capture is complete (so a token cut at the cap never reaches the model as a fragment), and `output_complete` says when the capture was cut short or has gone missing. Draining stops at a bound, not at EOF, so a descendant that leaves the group while holding the output pipe cannot hang the tool, and it makes the cleanup not clean. Background jobs return a `run_id`; `run_status` with no `run_id` lists them; `run_cancel` cancels only the tool's own jobs, by recorded process group, reports a job that already finished as it finished, and is idempotent. Jobs are recorded on disk keyed by process group, the first record right after spawn and before the deadline is armed; if that first write fails, termination is attempted (SIGTERM only if a first probe finds members of the group the tool may signal, then SIGKILL is attempted if no probe reports the group empty during the grace) and `run` refuses, saying whether its group was verified empty; the end of the run (pi's `session_shutdown`, or process exit) cancels every job the run still owns and logs each cleanup. The next session's boot sweep finds runs whose supervisor is gone — a dead pid, or a live pid that is no longer that supervisor (another process instance, another pinned identity, or — when the identity cannot be compared — a stale heartbeat) — deletes their captures, reports their jobs, and signals a job's group only while its leader still has the identity pinned at spawn (on Linux the boot id, start time in clock ticks, process group and session from `/proc`), re-checked before every signal; where no sub-second identity exists (macOS included) it signals nothing. Ended runs are swept by the 24-hour retention bound alone. S1 has no in-bob run wall clock: an unattended launch must be bounded by its launcher, and an in-bob `--max-runtime` supervisor lands with S4. `run` is in `RESIDENT_EXCLUDED_TOOLS` beside `bash` and `powershell`. It reuses pi's exported `getShellConfig`, `truncateTail` and `formatSize`; the process-group signal and probe move from the tps-mail consumer into `src/shell/process-group.ts`, shared by both (pi does not export its process-tree kill). The shared secret redaction (`redactSecrets`, used by the observatory's `sanitizeString` too) now also covers `Authorization` / `Proxy-Authorization` header values of any scheme, length and spacing (the whole value through the end of its line, quoted Digest parameters included; a value is left alone only when it is already entirely the placeholder), `*_TOKEN=`-style environment assignments and credentials in URL userinfo. The builder-local soul drops the explicit-timeout and pattern-kill procedures, keeps the prohibition on signalling any process outside `run`'s own jobs, and says what `run` is not: a process-group backend running as the same user, not a sandbox or containment, whose cancellation covers only its own jobs and whose escaped descendants may survive. (`test/capabilities/work/`, `test/shell/role-loader.test.ts`, `test/shell/mail-turn.test.ts`, `test/shell/tool-allowlist.test.ts`)

- **The `tps-mail` capability: a bob agent answers TPS mail (#200).** `bob run <name>` runs an inbox consumer that answers each accepted mail with ONE turn in a FRESH session through the agent's launcher — never in the warm session, so a reply draws only on what that turn read. Accepting happens before any session exists: the inner signed envelope is verified against the sender's key as registered in the agent's Flair (Ed25519 over RFC 8785 bytes — the CLI's own check, ported, pinned by envelopes the CLI's `signEnvelope` produced), its signed `from` is bound to the record's `from` and to `X-TPS-Sender`, the envelope must be addressed to the agent, and the verified id must be on the required, non-empty, exact-match `senders:` allow-list; anything else moves to `refused/` with a counted reason and is never answered (`X-TPS-Trust` is not consulted). New mail is processed one at a time, oldest first by filename. The turn runs through `bob launch` with `BOB_MAIL_TURN=1` and the verified fields on stdin (never argv), under a wall-clock timeout that kills the launcher; the task contract in the system prompt is the capability's fixed frame (the never-do list and the reply rule), and the mail body — control, bidi, zero-width and tag characters stripped, length-bounded — sits only in the user message, in a block delimited by per-turn random markers. A mail turn holds ONLY a reviewed allowlist — `flair_search`, `flair_get`, `flair_write`, where the role allows them — and every other tool from any role, position grant or capability is dropped (for an agent bound to a position the narrowing applies to the grant's resolved tools exactly as to a role's) (no file tool, including builder-local's anchored `read_lines`/`edit_lines`/`insert_after`/`write_file`, no shell, no Discord); keeping `flair_write` means allow-listing a sender also permits mail-influenced memory writes (documented). The reply is the turn's final message under the compaction contract's finality rule (tool-only, empty → no reply; error-ended → a failed turn), capped at `maxReplyChars`, sent with `tps mail send <sender> --stdin --reply-to <messageId>` (fixed argv, body on stdin, `TPS_AGENT_ID` = the agent's own id), then a DURABLE `replied/<messageId>` marker (temp + fsync + rename + directory fsync; any failure, a directory fsync included, leaves the mail un-acked, and bob tries to take the marker back), then the move to `cur/`. An EXISTING marker is trusted — to ack a re-delivery or to refuse a collision — only after bob has fsynced the `replied/` directory itself, so a marker left behind by a failed sync and a failed removal is never acked on; a failed sync is retried, after a restart too. A `replied/` directory that cannot be fsynced gets its own error and fails `bob doctor`, which inspects the `replied/` entry itself without following it (a broken symlink or a non-directory fails). The marker records the verified sender and a digest of the signed envelope (outer signature normalized to the verified bytes): a re-delivery of the same envelope acks with no second reply; a marker is used only after schema validation of every field bob writes (sender, digest, inboundId equal to this inbound, outcome, at), which cannot prove who wrote the file; an existing marker causes an `id-collision` refusal only after a successful read and schema validation show a different envelope, and pending-settlement or pending-reply state this run holds for the id causes it too; a marker read error is retried, and a marker that fails schema validation HOLDS the mail in `held/` with its `.reason` written before the move (counted, and shown by doctor). A marker that cannot be written leaves the mail un-acked and uncounted in `new/`, where the retry writes the marker without resending. A failed turn, an unreachable Flair, a failed send or a failed marker is counted, logged, and left in `new/` for a retry with backoff (a composed reply is resent without a second turn). Delivery is at-least-once: a second reply, threaded to the same `messageId`, is possible when the runtime dies before a durable marker or when the CLI timed out or exited non-zero after it may already have delivered; a record that cannot be checked (e.g. a non-finite number canonicalization cannot encode) is refused, since retry is reserved for the key service. The launcher runs as its own process group, which is reaped as soon as the launcher process EXITS or the turn is aborted — not when its output closes, so a descendant holding that output cannot hold up the turn or its result, except a member cleanup cannot kill (it still delays the result until the turn timeout): SIGTERM, then SIGKILL after a grace, probing on a nominal 50 ms poll interval (with no hard bound under event-loop delay) for up to the grace plus a reap limit, after which remaining members are logged with the group id and counted (`reapExhausted`); signals go only to a group a probe has just found. The turn gets the consumer pid at spawn and, before reading its input, requires it to be its parent; after that it ends when that pid is gone or it is reparented. The consumer lock is taken over only from a DEAD pid, never by age, through an exclusive claim keyed on that pid, so racing restarts end with exactly one holder; an empty lock, an empty claim, or a claim naming a dead process fails the start naming that file and when it is safe to remove it. Mail turns never enter the warm session's turn admission (#147) and are not reflected in presence: they run concurrently in their own process, and the roster holds one activity. `bob doctor` FAILS on a `channels.tps_mail` nothing honours, an invalid `tps-mail:` block (an empty `senders:` also refuses to load), a missing Flair identity, a missing inbox, a host that is not a TPS delivery target (#134), or a missing `tps`/signing key, and reports refused counts per reason, turn failures and reply failures. Allow-listing a sender grants it the agent's read scope (documented). STATED LIMITS: the reply needs a `tps` that accepts `--stdin` and `--reply-to`, which `tps` 0.7.0 does not — until it does every reply fails closed (counted, retried); `tps` 0.7.0 also cannot read the PEM key `bob onboard` writes. (`test/capabilities/tps-mail/`, `test/shell/mail-consumer.test.ts`, `test/shell/mail-turn.test.ts`, `test/shell/doctor.test.ts`, `test/shell/persistent.test.ts`, `test/shell/launch.test.ts`, `test/shell/positions-195.test.ts`)

- **Positions — packaged, role-compatible agent presets, and the host trust root that governs them (bob#195 slice 1).** A new packaged `positions/` directory ships two first-party presets, `builder` and `reviewer`, each naming an existing role (it never carries or edits one) and declaring the tools it requests, the capabilities it permits (and which are on by default), and the packaged files it uses (a seed soul; skill, prompt and threshold files are later slices, and a manifest that declares one is refused until it loads). Three commands land: `bob hire <name> --as <position>` (scaffold a NEW agent, ratify the host grant, store the diff baseline, initialize the override repository, and run the existing hiring interview, which keeps the agent's own identity in its seed soul — the identity header plus the position's persona, not the generic packaged soul alone), `bob position adopt <name> --as <position>` (bind an EXISTING agent without rewriting it — it independently resolves the agent before and after binding, REQUIRES the two effective configurations to be equal or refuses, verifies its requests against the position, role and new grant, records the binding, ratification and normalized baseline, initializes the override repository, and leaves the pre-existing `bob.yaml` and `soul.md` byte-for-byte unchanged), and `bob position diff <name>` (the ratified baseline against the current effective configuration, comparing role, tools, tool exclusions, the residency decision, the resident-shell grant, capabilities, resolved files and the soul). A **host grant** ratifies the role name, the position name/version/hash, the maximum tool set and the maximum capability set. The grant file is stored under the host state root, but that placement is NOT a containment boundary — any same-user writer, including the agent's own built-in file tools, can edit it — so what it gives is boot checks, not authentication: Boot checks a grant against the packaged position selected by that grant and its role; it refuses a previously bound agent with a missing or unreadable grant, but it does not authenticate the grant or detect every same-user edit. Isolation from same-user writes is deferred to bob#189. - **Every launch path enforces the tool policy.** The generated `bin/<name>` launcher used to start a session of its own, onboard and align started one directly, and the mail consumer reached the session through the launcher — so every path outside `bob run` came up on whatever pi defaults to, whatever the role said. The launcher now hands off to `bob launch`, which resolves the agent's policy (`role.json` + `bob.yaml`) and starts the session through the ONE factory; onboard, align and the mail consumer go through that same factory. No path starts an agent session without the resolved allowlist. (`test/shell/launch.test.ts`, `init.test.ts`, `onboard.test.ts`, `align.test.ts`)
- **A missing or unparseable tool policy is a load error, not pi's defaults.** An absent `tools:` block, a `tools:` block with no `allow:`, and the inline form (`tools: {…}`, refused outright) all used to end up as "pi's defaults", which is the absence of a policy rather than one. An explicit empty list (`allow:` with no items) is still valid and means no tools, and the resolved allowlist and denylist reach the session as the factory's `tools`/`excludeTools`. `bob doctor` reports a missing policy as FAIL with the fix. (`test/shell/tool-allowlist.test.ts`, `doctor.test.ts`)
- **An allowlisted tool the session does not actually have is a load error naming it.** pi enables only what the loaded capabilities register and IGNORES an unknown tool name silently, so a role allowlist naming a capability tool (e.g. the EA role's `discord_reply`) on an agent that does not declare that capability produced a session quietly missing the tool its role asked for. A tool named in `tools.allow` that is not active after the capabilities load — and that no `tools.exclude:` removed — fails the session, naming the tool and pointing at `capabilities:` in `bob.yaml`: what registers a tool is the capability's extension, which has already loaded by then, so the message names the tool rather than the capability that would provide it. `bob doctor` reports the same condition before any session runs, and it works from the agent's DECLARATION: it flags an allowlisted capability tool whose capability `bob.yaml` does not declare. (`test/shell/run-tool-allowlist.test.ts`, `doctor.test.ts`)
- **`bob doctor` no longer suggests a fix that would fail.** A resident agent whose allowlist names a tool the resident policy drops used to be told to set `tools.allowResidentShell: true` in `bob.yaml` — which the role ceiling refuses at load, because `bob.yaml` may only narrow the role. The hint now names `roles/<role>/role.json`, where the grant actually lives, and names the `tools.allowResidentShell: false` denial in `bob.yaml` when that is what holds the tools down. (`test/shell/doctor.test.ts`)
- **`bob doctor` reports the FAILURE when an agent trips both of its tool checks.** A resident agent whose allowlist carried a dropped shell tool AND a tool of an undeclared capability used to get only the resident warning; the missing capability now fails first, because that is what would stop the session. The capability check also skips names the denylist removes, matching the session's audit. (`test/shell/doctor.test.ts`)
- **`bob init` stamps a policy that loads for every role:** the role's ceiling intersected with the tools that can exist for that agent (pi's built-ins plus the tools of the capabilities bob stamps). A fresh agent no longer carries a name nothing can register. (`test/shell/init.test.ts`)
- **The refused inline `tools:` form has a dedicated test.** `tools: {allow: [read]}` reads as an empty block — and empty is one step away from pi's defaults — so it is refused outright, naming the block shape to use. (`test/shell/tool-allowlist.test.ts`)

### Notes

- **Stated limits of the contract above.** The task is sent in the first user message AND in every agent request's system prompt, so it costs tokens per request (the appended block is identical on every request of a run — pi rebuilds the prompt around it when the active tool set changes or on a reload, and the same text is appended each time — so a provider's prompt cache can cover it; it is not shared across runs). A failed best-effort "what remains" note can lose the text it would have quoted — the TASK is not lost, it is in the system prompt. And the completion judge checks for a real final MESSAGE, not that the work it describes was actually done.

## [0.1.0] - 2026-05-21

First publishable release. Bob is functional end-to-end: scaffold an agent with `bob onboard`, shape its persona through conversation, run it via `bob run`, keep it listening on Discord via `bob serve --discord`, and health-check it with `bob doctor`.

### Added

- **`bob onboard <name> --role <role>`** — scaffolds the per-agent directory layout (soul.md, bob.yaml, Ed25519 keypair, executable launcher, pi-agent config) and drops into an interactive hiring interview where the agent writes its own persona via conversation with the human. `--no-interactive` skips the interview for CI/dry runs. `--dry-run` previews the plan.
- **`bob align <name>`** — recurring drift-check counterpart. Spawns an alignment conversation; agent rewrites soul.md with the deltas surfaced.
- **`bob run <name> [prompt]`** — invoke an agent's launcher with optional `--model X` per-call override (lightweight dynamic routing) and `--interactive` for a TUI session.
- **`bob serve <name>`** — daemon mode. Mail consumer always-on. Add `--discord --discord-token-file <p> --discord-channels <ids> [--discord-dispatch-all] [--discord-model <m>]` to attach a Discord listener that dispatches @-mentions (or all messages in dispatchAll mode) through `runAgent` and posts the captured stdout back to Discord.
- **`bob doctor <name>`** — health check that walks the expected layout and reports per-check status (OK / WARN / FAIL / SKIP) with actionable `fix:` hints. Exit 1 on any FAIL. Read-only — never modifies state.
- **Five role templates** ship in `packages/shell/roles/`: `ea`, `writer`, `reviewer`, `coder`, `qa`, plus a blank-slate `custom` stub. Each role has a seed `soul.md` (What you own / Don't own / Personality / Tone / Failure modes) and a `role.json` with a sensible tool allowlist and provider/model defaults.
- **Launcher generation** writes a per-agent `~/.pi-agent/auth.json` (placeholder API key) and `models.json` (gateway baseUrl override) when provider is `exe-dev-gateway`, and appends `--append-system-prompt "$(cat $AGENT_DIR/soul.md)"` so the agent loads its persona on every invocation.
- **Identity** via Ed25519 keypair generation + Flair Agent record registration.
- **Discord bridge abstraction** (shell) + discord.js binding (separate `@tpsdev-ai/bob-discord` package so callers without Discord don't pay the ~30MB discord.js install cost).
- **stdout capture** in `runAgent` so the Discord listener can post the agent's reply.
- **Path-traversal + prompt-injection defense** at the entry of every agent-name-accepting function: `runOnboard`, `runAlign`, `runAgent`, `runDoctor`. AGENT_NAME = `/^[a-z0-9-]+$/`.

### Architecture

Bob is a thin TypeScript shell on top of [pi-coding-agent](https://github.com/earendil-works/pi). Pi owns the agent loop, tools, and LLM provider abstraction. Bob adds the office plumbing — identity, mailbox, channels, scheduling — that turns one terminal agent into a named office hire.

### Packages

- `@tpsdev-ai/bob` — the `bob` CLI command
- `@tpsdev-ai/bob-shell` — runtime + role templates + integrations (mail, Discord bridge abstraction, init, run, onboard/align, doctor)
- `@tpsdev-ai/bob-discord` — discord.js binding for `bob-shell`'s `DiscordClient` interface

### Status

`0.1.0` is the first publishable release. First production deployment is **Pulse-EA** on a fresh `tps-pulse` VM. The interactive onboard flow, real `bob run`, Discord listener with auto-reply, doctor, role templates, and per-agent pi config seeding all landed in PR-15 through PR-22.

Known caveats:
- Federation pair (Bob agents reading/writing Flair memory across hosts) requires the same setup as Reed Phase 2; not packaged into `bob office join` yet.
- Branch-office docs (`bob office join`) are stubbed pending the productization recipe from `~/ops/specs/`.
