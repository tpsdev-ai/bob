- **The discord outbound tools are bound to the running turn's channel (bob#227).** Reply routing to each inbound message's own channel and message was already correct on `main` — each inbound message's callback captures its own destination — so this is a hardening of the outbound TOOLS, not a routing change; the routing assertion is a regression pin. While a discord turn is running, `discord_reply`, `discord_react` and `discord_fetch` may act on only that turn's channel — and a quoted `replyTo` / a reaction `messageId` must name a message in that channel; a different channel, or a message that cannot be shown to belong to it, is refused even when the channel is on the allow-list. Only the origins that are NOT a chat surface are exempt (a bare `run`, a `cron`/heartbeat turn); any other origin kind (a `mail` turn, or an unknown one) is refused rather than allowed, and outside an admitted turn (a one-shot `bob run`) the channel allow-list is the only boundary. The turn's destination is an immutable identity (`channelId`, `messageId`, `authorId`, `guildId?`, `isDM`) captured at dispatch, and a message that arrives mid-turn is queued as its own turn. This binds the outbound tools to the turn's channel; the conversation context is still shared across channels and DMs, so channel isolation is NOT provided until per-channel history lands (tracked in #234). The message lookup behind that check (`DiscordJsClient.fetchMessage`) reads a 404 as "not in this channel" and throws every other failure (a 403, a 5xx, a rate limit the REST manager surfaces, a transport error) rather than reporting it as not found; it is pinned through the real client with only the transport stubbed. (`test/capabilities/discord/capability.test.ts`, `test/capabilities/discord/fetch-message.test.ts`, `test/shell/turn-admission.test.ts`)
- **`bob doctor` FAILS a `tps` that cannot send bob's replies, and tps-mail refuses a malformed signed `replyToId` as the CLI does (#200).** Every reply goes out as `tps mail send <to> --stdin --reply-to <messageId>`, the contract tpsdev-ai/cli#431 added; with `tps` 0.7.0 or older every reply fails closed, yet doctor's reply-transport check passed, so the agent looked mail-capable and never answered. A new `tps-mail reply contract` check runs `tps mail --help` (fixed argv, no shell, an environment of `PATH` and `HOME` only, a 10 s bound) and FAILS unless the CLI's mail usage names both flags; a probe that cannot start, times out or exits non-zero FAILS too, naming what it saw. The accepting step now applies the CLI's envelope-id rule (1-128 letters, digits, dots, underscores or hyphens) to a signed `replyToId` when the envelope carries one, as the CLI's receipt policy does, and refuses it as `malformed` otherwise. A reply the CLI itself signed with `--reply-to` is pinned as a fixture: bob accepts it and refuses it with the `replyToId` altered or removed. The README's stated limit now names the CLI change. (`test/shell/doctor.test.ts`, `test/capabilities/tps-mail/envelope.test.ts`)
- **The discord capability can make REST calls again under the global undici 8 override (bob#217).** The capability's Discord client now hands discord.js's REST manager its own request function, which performs the call with the runtime's global `fetch`. @discordjs/rest's own request strategy builds the response with `new Headers(res.headers)`; under Node the pinned `undici` negotiates HTTP/2, Node's HTTP/2 client marks that headers object with a `Symbol(sensitiveHeaders)` key, and undici's `Headers` constructor rejects a symbol key — so on the override as it stands no REST call can complete, and that REST failure blocks the agent's gateway from being set up (opening the gateway is a later, separate stage). The global `fetch` does not go through the pinned `undici` package, so the request completes. The request function forwards only the method, the body, the string-keyed headers and the abort signal: it drops any dispatcher the manager supplies (this binding never sets an agent, and a dispatcher from the pinned `undici` is incompatible with the runtime's `fetch`), and it refuses to follow redirects, so a cross-origin 3xx fails with the status and the target host instead of letting the request leave unauthenticated. `bun audit` stays clean. (`test/capabilities/discord/rest-connection.test.ts`, `test/capabilities/discord/rest-request.test.ts`)
- **The installed service unit runs bob under Node, with an absolute interpreter path resolved at install time (bob#218).** `bob install-service` writes `<node> <bob> run <name>` into both the launchd `ProgramArguments` and the systemd `ExecStart`, where `<node>` is an absolute Node executable — the installer's own interpreter when it is Node, otherwise the `node` found on the installer's PATH. launchd and systemd both launch a unit with a minimal PATH, and bin/bob's `#!/usr/bin/env node` shebang resolved the interpreter through that PATH — so a node installed outside `/usr/bin` (Homebrew, nvm) was not found and the job exited 127, restarting every throttle interval without ever starting the agent. A bun-launched install no longer writes a unit that runs bob under bun (bin/bob's shebang and the package's `engines` require Node): installation REFUSES, naming the remedy, when no Node is found, and writes nothing. An already-installed unit keeps its old command until it is rewritten, so reinstall it after an upgrade (`bob down <name>`, `bob install-service <name>`, `bob up <name>`). The unit still embeds no secret. (`test/shell/service.test.ts`)
- **A resident agent keeps a tool only when a reviewed classification says it writes no file and runs no command (bob#213).** Every tool an agent's allowlist can name (pi's built-ins and every tool a blessed capability's manifest declares) has a reviewed row in `TOOL_EFFECTS` (`src/shell/tool-allowlist.ts`): `read-only`, `writer` (writes a file the model names, or runs a command) or `effect` (a memory write, a Discord post or reaction, a status report, a robot action, cancelling a job this run started). `RESIDENT_EXCLUDED_TOOLS` is derived from it: every `writer`, plus any declared name without a row. It now includes anchored-edit's `write_file`, `edit_lines` and `insert_after` beside `bash`, `write`, `edit`, `powershell` and `run`, so a resident agent without its role's `allowResidentShell` opt-in no longer keeps them; builder-local, the one shipped role that lists them, opts in. A test enumerates the manifests' tools and fails on a name without a row, and on a row no manifest or pi built-in provides. (`test/shell/tool-allowlist.test.ts`)
- **`run` refuses a `cwd` outside the workspace (bob#213).** The `cwd` is resolved through symlinks, and a directory outside the workspace is refused, naming the workspace and the resolved path; nothing starts. A directory inside the workspace whose name starts with two dots (`..cache`) is accepted. Tests cover a relative path inside, a `..` escape, a `..cache` directory, and a symlink inside the workspace to an existing directory outside it. The `cwd` parameter description and the capability README name both accepted forms: relative to the workspace, or an absolute path inside it. (`test/capabilities/work/boot-sweep.test.ts`)
- **`bob init --role builder-local` stamps neither `bash` nor `run` (bob#213).** A test pins the stamped list (`grep`, `find`, `ls` and the three Flair tools) and shows the run tools are stamped only when `work` is among the capabilities; the `work` capability's README says it is what enables `run`. (`test/shell/init.test.ts`)
- **README: where a restarted agent reports what a crashed run left (bob#213).** The boot sweep logs each job a crashed run left that it can inspect to the runtime log and attempts to record it in the job's registry record (`reaped_by`, a write that can fail); none of it enters the restarted session's model context. The README now says so.
- **Flair Soul provisioning now uses operator Basic auth.** `bob onboard` and `bob align` read the operator password from `~/.flair/admin-pass` at each Soul push (`--admin-pass-file` overrides the path; `--admin-user` overrides `admin`). `bob align` requires an operator-supplied `--flair-url` matching the agent's configured URL. Basic auth is sent only to HTTPS or numeric loopback HTTP targets, and Soul writes refuse redirects. The divergence read stays agent signed and still saves the previous persona byte for byte on conflict. A missing password file fails with an actionable path and remedy. The operator password is read at call time, removed from the process environment and never passed to an agent session: bob takes `FLAIR_ADMIN_PASS` out of its environment at startup and hands the value only to Agent registration, and bob's session factory removes the variable again before any session (the hiring and onboarding interviews, align, run, launch) is built. It is not isolated from same-user file access, which is tracked separately, nor from a same-user process that reads bob's initial environment. This fixes `403 soul_write_requires_operator` on current Flair. (`test/shell/flair-soul.test.ts`, `flair-provision.test.ts`, `operator-credential-env.test.ts`, `test/cli.test.ts`)
- **Operator-authorized Flair requests never print the server's response or a transport error.** A failed ops-API registration request now reports its status, operation, table and where the operator credential came from (`FLAIR_ADMIN_PASS` or the admin-pass file), never the response body, which is not read; the Soul writer follows the same rule. An exception from sending a registration or Soul request, or from reading its response, is replaced by an error naming only the operation, the target origin and the remedy, with no cause attached. Tests cover registration and Soul writes, directly, through `onboard` and `align`, and through the built CLI, and assert that no form of the credential reaches the error, stdout or stderr. (`test/shell/flair-pair.test.ts`, `flair-soul.test.ts`, `flair-provision.test.ts`, `test/cli.test.ts`)
- **Agent registration no longer reports a repair it did not make.** A refused Agent insert is treated as a concurrent registration only when a fresh read finds the Agent record; otherwise the insert's own error is reported. After updating a record's public key, registration reads the record back and reports `repaired` only when it carries the requested key. If the update request fails or the update did not take effect, registration fails and reports the insert error when an insert was refused. (`test/shell/flair-pair.test.ts`)
- **The setup sessions replace pi's unrestricted `write` with a bob-owned, soul-only `write_soul` (bob#204).** `bob onboard`'s hiring interview and `bob align` added pi's generic `write` so the interview could write the agent's refined `soul.md` — but pi's `write` accepts ANY absolute path the OS user can write, so a setup session could rewrite `bob.yaml`, capability overrides, grants, launcher scripts, or files outside the agent directory. Every setup session — an ordinary agent's and an ADOPTED agent's alike (not the grant's tools plus `write`) — now runs exactly `read` + `write_soul`: a bob-owned tool (`src/shell/write-soul.ts`) that takes `content` and nothing else (every other argument key is refused, and its schema allows no other property). Its one target is `soul.md` in the directory the session runs as. Before the session starts, bob canonicalizes the agents root once and uses that one tree for the session's config, its paths and the binding, and it refuses an `--agent-dir` that names a different agent's directory. On every call the tool refuses a symlink in ANY component of that path, caps the content at 64 KiB, writes every byte (honoring partial writes, refusing zero progress), fsyncs, and only then renames over `soul.md`. An existing `soul.md` keeps its permission bits; a new one is `0600`. Threat model, stated: this defends against the setup session's OWN tool calls. The model holds only `read` and `write_soul`, with no shell, and whatever arguments it sends, the one file it can write is the bound `soul.md`. A concurrent local process that renames directories inside the agents tree already has the user's write access and is out of scope. On Linux the temp creation, rename and cleanup go through the open directory handle (`/proc/self/fd`). On macOS, where Node offers no directory-relative calls, they use the path, re-checked immediately before each step; those checks are best effort against such a process, not a guarantee. The temp (`.soul.md.write_soul-<pid>-<24 hex>.tmp`) is created exclusively and held open until the rename is confirmed. On a failure, a call removes only the temp it created (name and inode). Nothing is deleted on name-and-age evidence, so a crash can leave a temp in the agent directory; bob never reads it, and it is safe to delete by hand. Limit, stated: an agent running as the operator's OS user with a shell or unrestricted read can still reach operator files directly — that needs the OS boundary (bob#189), which this does not replace. (`test/shell/write-soul.test.ts`, `onboard.test.ts`, `align.test.ts`, `positions-195.test.ts`)
- **Position hire and grant handling (bob#195 slice 1).** `hire` refuses the unsupported `--flair` flag before scaffolding, including when the flag precedes the agent name; direct hire calls also refuse Flair opt-in. Every grant reader now rejects malformed grant JSON with a named refusal and recovery instruction. Override repository setup ignores operator Git signing, hook and template settings. The hiring interview uses the same host and positions roots as hire validation and binding.

## [0.2.0] - 2026-05-23

Intel-gathering ergonomics for Bob agents. The launcher template now wires up GitHub-authenticated reads by default — no hand-patching when a Bob agent needs to poll releases.atom or hit the REST API.

### Added

- **GitHub PAT sourcing in the launcher template** (PR-26). `bob init` now emits an opt-in block that sources `$HOME/.tps/secrets/<name>-github-pat` into `GH_TOKEN` at startup. Lifts the GitHub rate-limit ceiling from ~60/hr (anonymous, shared exit IP) to 5000/hr (authenticated). Silent no-op when the file is missing — agent still runs on the anonymous limit. Per-agent PAT identity (not a shared bot) so a leak rotates one identity, not the org. The companion [@tpsdev-ai/skills/intel-gathering](https://github.com/tpsdev-ai/skills/tree/main/intel-gathering) skill pack documents the full pattern (PAT scope, verified-working vendor feeds, polling cadence, ETag caching).

### Changed

- **README polish** (PR-24). Three fixes from Nathan's review pass: provider-name corrections + clearer composition story.
- **`bob onboard` interview prompt** (PR-25). "What would you say... ya do here?" Office Space callback shipped + "Bring On Board" backronym added to the README.

### Notes

No breaking changes. Existing Bob agents continue to work; the new launcher block only matters at next `bob init` (or when an agent has a PAT file under `~/.tps/secrets/<name>-github-pat`, which never auto-magically appears — you have to drop it).

## [0.1.0] - 2026-05-21

First publishable release. Bob is functional end-to-end: scaffold an agent with `bob onboard`, shape its persona through conversation, run it via `bob run`, keep it listening on Discord via `bob serve --discord`, and health-check it with `bob doctor`.

### Added

- **`bob onboard <name> --role <role>`** — scaffolds the per-agent directory layout (soul.md, bob.yaml, Ed25519 keypair, executable launcher, pi-agent config) and drops into an interactive hiring interview where the agent writes its own persona via conversation with the human. `--no-interactive` skips the interview for CI/dry runs. `--dry-run` previews the plan.
- **`bob align <name>`** — recurring drift-check counterpart. Spawns an alignment conversation; agent rewrites soul.md with the deltas surfaced.
- **`bob run <name> [prompt]`** — invoke an agent's launcher with optional `--model X` per-call override (lightweight dynamic routing) and `--interactive` for a TUI session.
- **`bob serve <name>`** — daemon mode. Mail consumer always-on. Add `--discord --discord-token-file <p> --discord-channels <ids> [--discord-dispatch-all] [--discord-model <m>]` to attach a Discord listener that dispatches @-mentions (or all messages in dispatchAll mode) through `runAgent` and posts the captured stdout back to Discord.
- **`bob doctor <name>`** — health check that walks the expected layout and reports per-check status (OK / WARN / FAIL / SKIP) with actionable `fix:` hints. Exit 1 on any FAIL. Read-only — never modifies state.
- **Five role templates** ship in `packages/shell/roles/`: `ea`, `writer`, `reviewer`, `coder`, `qa`, plus a blank-slate `custom` stub. Each role has a seed `soul.md` (What you own / Don't own / Personality / Tone / Failure modes) and a `role.json` with a sensible tool allowlist and provider/model defaults.
- **Launcher generation** writes a per-agent `~/.pi-agent/auth.json` (placeholder API key) and `models.json` (gateway baseUrl override) when provider is `exe-dev-gateway`, and appends `--append-system-prompt "$(cat $AGENT_DIR/soul.md)"` so the agent loads its persona on every invocation.
- **Identity** via Ed25519 keypair generation + Flair Agent record registration.
- **Discord bridge abstraction** (shell) + discord.js binding (separate `@tpsdev-ai/bob-discord` package so callers without Discord don't pay the ~30MB discord.js install cost).
- **stdout capture** in `runAgent` so the Discord listener can post the agent's reply.
- **Path-traversal + prompt-injection defense** at the entry of every agent-name-accepting function: `runOnboard`, `runAlign`, `runAgent`, `runDoctor`. AGENT_NAME = `/^[a-z0-9-]+$/`.

### Architecture

Bob is a thin TypeScript shell on top of [pi-coding-agent](https://github.com/earendil-works/pi). Pi owns the agent loop, tools, and LLM provider abstraction. Bob adds the office plumbing — identity, mailbox, channels, scheduling — that turns one terminal agent into a named office hire.

### Packages

- `@tpsdev-ai/bob` — the `bob` CLI command
- `@tpsdev-ai/bob-shell` — runtime + role templates + integrations (mail, Discord bridge abstraction, init, run, onboard/align, doctor)
- `@tpsdev-ai/bob-discord` — discord.js binding for `bob-shell`'s `DiscordClient` interface

### Status

`0.1.0` is the first publishable release. First production deployment is **Pulse-EA** on a fresh `tps-pulse` VM. The interactive onboard flow, real `bob run`, Discord listener with auto-reply, doctor, role templates, and per-agent pi config seeding all landed in PR-15 through PR-22.

Known caveats:
- Federation pair (Bob agents reading/writing Flair memory across hosts) requires the same setup as Reed Phase 2; not packaged into `bob office join` yet.
- Branch-office docs (`bob office join`) are stubbed pending the productization recipe from `~/ops/specs/`.
