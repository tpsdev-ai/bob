- **The setup sessions replace pi's unrestricted `write` with a bob-owned, soul-only `write_soul` (bob#204).** `bob onboard`'s hiring interview and `bob align` added pi's generic `write` so the interview could write the agent's refined `soul.md` — but pi's `write` accepts ANY absolute path the OS user can write, so a setup session could rewrite `bob.yaml`, capability overrides, grants, launcher scripts, or files outside the agent directory. Every setup session — an ordinary agent's and an ADOPTED agent's alike (not the grant's tools plus `write`) — now runs exactly `read` + `write_soul`: a bob-owned tool (`src/shell/write-soul.ts`) that takes `content` and nothing else (every other argument key is refused, and its schema allows no other property). Its one target is `soul.md` in the directory the session runs as. Before the session starts, bob canonicalizes the agents root once and uses that one tree for the session's config, its paths and the binding, and it refuses an `--agent-dir` that names a different agent's directory. On every call the tool refuses a symlink in ANY component of that path, caps the content at 64 KiB, writes every byte (honoring partial writes, refusing zero progress), fsyncs, and only then renames over `soul.md`. An existing `soul.md` keeps its permission bits; a new one is `0600`. Threat model, stated: this defends against the setup session's OWN tool calls. The model holds only `read` and `write_soul`, with no shell, and whatever arguments it sends, the one file it can write is the bound `soul.md`. A concurrent local process that renames directories inside the agents tree already has the user's write access and is out of scope. On Linux the temp creation, rename and cleanup go through the open directory handle (`/proc/self/fd`). On macOS, where Node offers no directory-relative calls, they use the path, re-checked immediately before each step; those checks are best effort against such a process, not a guarantee. The temp (`.soul.md.write_soul-<pid>-<24 hex>.tmp`) is created exclusively and held open until the rename is confirmed. On a failure, a call removes only the temp it created (name and inode). Nothing is deleted on name-and-age evidence, so a crash can leave a temp in the agent directory; bob never reads it, and it is safe to delete by hand. Limit, stated: an agent running as the operator's OS user with a shell or unrestricted read can still reach operator files directly — that needs the OS boundary (bob#189), which this does not replace.
