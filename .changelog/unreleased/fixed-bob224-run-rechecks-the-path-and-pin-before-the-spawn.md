- **`run` re-checks the requested path and the pin before the spawn, narrowing the race between the check and the spawn (bob#224).** Checking `cwd` and spawning the command were separate steps. `run` now resolves `cwd` and the workspace through symlinks (a path that cannot be resolved is refused, never guessed), opens the resolved path and holds it open as the pin (no-follow on the final component), and — as the pin is taken, and again immediately before the spawn — re-resolves `cwd`: it must still be the same canonical path, inside the canonical workspace checked first, and a no-follow stat of it must still show the pinned device + inode, compared at full 64-bit precision (as bigints, so identities that differ only beyond a JavaScript number's precision are not taken as equal). If, at either re-check, a final or intermediate path component has been replaced or moved so that this no longer holds, `run` refuses and starts nothing; it also refuses when any pin step fails (realpath, stat, open, fstat or close), and a realpath that fails (when `cwd` is first resolved, or at a re-check) or a re-check's no-follow stat that fails is reported as a failure to resolve or check, with no cause assigned. A failed close of the pin's descriptor is reported, not suppressed, even when the final re-check failed too (the refusal then reports both): the refusal says that whether the descriptor is still open is unknown, and it says the descriptor was closed only when the close returned. The pin's release (the close of its descriptor) comes before the spawn, and a release that fails refuses, so no pin step can fail after a command has started. The re-check NARROWS the race; it does not close it: a window remains from the last re-check until the child has changed directory, because Node names a child's working directory by a string that the child's `chdir` resolves again (Node has no `fchdir` and cannot hand a child a directory descriptor as its cwd), stated in the capability README's Limits. The pin is taken after `cwd` is resolved, so a replacement between the resolution and the pin that keeps the same canonical path inside the workspace becomes the pinned directory; containment still holds, and the capability README's Limits state this too. The pin opens the directory for reading, so a directory with search but not read permission is refused, although a command could start in it. The test seams (`beforePin`, `beforeSpawn`) are synchronous and called only when set, so `start` does not yield between its live-job limit check and the job's registration; the pin's file-system calls are a seam (`dirPinOps`) through which tests inject the realpath, stat, fstat and close failures; the open failure is exercised with directory permissions instead (search but no read), in a test skipped when running as root.
