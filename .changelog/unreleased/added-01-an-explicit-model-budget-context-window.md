- **An explicit model budget: context window, compaction between model calls, thinking level, an output-cap backstop, per-request usage (#214).** Measured on a local builder, decode ran about 99 tok/s at 16k context or less and about 44 tok/s above 192k. Contexts ran to the server's limit because the runtime's window (131k) was not the server's (262k) and compaction was only checked when a run ended. bob.yaml's `provider:` block now takes `context_window` (required: every session refuses to start without a window for the provider/model it runs, naming bob.yaml and the key that would declare it), `max_output_tokens`, and `models:` entries for `--model` overrides (`bob run --model` and `bob align --model` both resolve them; `bob align --provider` naming a provider other than bob.yaml's is refused, since bob.yaml declares windows for its own provider only). The declared numbers are what pi's runtime uses for that model. A new `session:` block (`compaction_threshold`, `thinking: off | low | high`) overrides the role's `session` defaults in role.json; `builder-local` ships `0.5` and `low`. The threshold sets pi's own compaction reserve. bob also checks it after every model call that ended in tool calls; over it, bob queues a checkpoint message and ends pi's low-level loop at that turn boundary, so pi's own compaction runs mid-run and the run continues. The thinking level is handed to pi, which sends it to the provider only when pi's model config marks the model as reasoning and the provider's request shape accepts the parameter (for example `reasoning_effort` on the OpenAI-compatible path); whether a server acts on it is the server's behaviour. `max_output_tokens` sets the output cap pi requests, in whichever output-limit field the provider's API uses (for example `max_completion_tokens`, `max_tokens` or, on OpenAI's Responses API, `max_output_tokens`; that API's client raises a cap below 16 to 16); for a server that ignores it, bob adds a backstop that ends the stream as a `length` stop after more streamed pieces than the cap. It counts pieces, not tokens: never early (a server sends a piece only after generating at least one token), possibly late (a piece can carry many tokens). The ended message holds only the pieces bob accepted, and its usage is assigned (`output` = the cap, a lower bound; prompt counts 0), not measured. Every run log carries a `requestUsage` record per request (prompt, cached-prompt, completion and thinking tokens, time to first streamed piece, duration, stop reason, provider and model); the record holds counts and timings, no prompt or response text. `bob onboard` and `bob hire` require `--context-window <tokens>` and refuse without it before writing anything. **Upgrade note:** an existing agent's bob.yaml needs `provider.context_window` (and a `provider.models:` entry for each `--model` it runs) before its next session. Unknown keys in `provider:` are now refused. (`test/shell/model-budget-214.test.ts`, `init.test.ts`, `cli.test.ts`)
