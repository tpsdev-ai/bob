- **`work` gains `apply_patch` and a launcher-supplied task binding (Refs #275, slice S2a).** The task binding — task/publication identities, repository and workspace, pinned base commit, mode, artifact root, declared paths, check commands and publication destination — comes from the launcher and reaches the capability through the ONE session factory (`BOB_TASK_BINDING`), kept independently of model messages; a missing or malformed binding refuses the dependent operation (`unknown_task` / `invalid_binding`), and no tool argument, repository file or agent-writable `bob.yaml` can supply it. `apply_patch` reads the artifact once, verifies its digest, and applies those verified bytes to a fresh, tool-owned `GIT_INDEX_FILE` initialized from the pinned base — supporting adds, modifications, deletions, renames, executable-bit changes and binary patches, and refusing symlink/submodule changes. It returns `{ candidate_id, base_oid, patch_sha256, tree_oid, changed_paths }` and stores the candidate with its task and repository association; a candidate id is not permission to publish. `publish`, candidate checks and publication recovery are S2b.
